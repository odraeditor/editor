# Why Language Workflows Use Static Package Boundaries

Odra keeps language recognition, language-service orchestration, and
application presentation in separate Odin packages. The boundary is static:
it does not introduce shared libraries, plugin loading, or another process.
The Odin compiler resolves the package graph while building the executable.

## Dependency Direction

```text
language and language_service contracts
                 |
                 v
         syntax_workflow
                 |
                 v
   language_service_workflow
                 |
                 v
       odra composition adapters
                 |
                 v
       commands and presentation
```

`syntax_workflow` owns filename recognition, provider selection, retained
syntax analysis, and syntax inspection. `language_service_workflow` owns
service catalog publication, process sessions, document synchronization,
diagnostics, health projection, and copied inspection rows. `src/odra` owns
composition with the editor session, completion, commands, Status Bar, and UI
rendering.

Dependencies point toward contracts and retained workflow state. The lower
packages never import the application package. Completion integration crosses
the service boundary through a narrow callback record; the application
adapter remains the owner of completion state.

## Why This Changes the Feedback Loop

A focused language change no longer requires compiling the complete
application package and linking the editor executable. Use:

```sh
make syntax-workflow-test
make language-workflow-focused-test
```

The first target validates recognition and retained syntax behavior. The
second validates syntax plus language-service reconciliation, process,
configuration, diagnostics, and inspection behavior. The complete executable
is still built for integrated acceptance and nightly verification, but it is
not the ordinary edit-test loop.

Racket tests run through a repository wrapper that enables `raco test --make`.
Racket stores compiled modules in ignored `compiled/` directories beside the
owning modules and continues to use its installation cache. Each worktree
therefore has independent compiled state, unchanged modules are reused, and
generated bytecode is never committed. Each invocation appends its elapsed
time and result to `.build/timings/racket-tests.log`.

Application builds export Odin timing data under `.build/timings`. The timing
records separate compiler work from the later Racket acceptance commands, so
an integrated run can attribute elapsed time instead of reporting one opaque
duration.

## Development Continuity

Complete application acceptance is not part of the interactive edit-test loop.
Daytime work closes with focused package checks. One exact integrated candidate
is left to Forgejo after the development window, and its result is inspected at
the start of the next window without blocking the preceding work session.

An explicitly requested local complete run uses the nightly's 150-minute
deadline, does not overlap Forgejo, and uses the proportional repository memory
profile instead of fixed GiB thresholds. Exhaustive acceptance is never
repeated immediately after a focused correction.

## Adding Language Support

A recognition-only language is catalog data: add its identity and filename
selectors through the public Racket configuration described by the
[Language Support Configuration Reference](../../reference/language-support-configuration/).
No native parser or server is required.

A conforming external language server adds a service definition for an
existing or newly configured language. The shared service workflow continues
to own executable resolution, project containment, initialization,
synchronization, diagnostics, restart policy, and teardown. Adding Go, Rust,
TypeScript, JavaScript, HTML, or CSS therefore normally changes declarative
language and service definitions, not application composition.

A maintained native syntax provider is a different extension: it adds parser
ownership to `syntax_workflow` and must satisfy the syntax contracts and
resource policy. That choice is required only when Odra needs native syntax
analysis rather than filename recognition and language-server features.

## Nightly Ownership

The scheduled workflow remains the sole exhaustive daily gate. Forgejo's
reported event field is not used to identify a nightly because scheduled and
manual runs may expose incorrect or empty event metadata. The first
`nightly.yml` run for the Warsaw local date is canonical; later runs exit
before toolchain verification or compilation. `make nightly-dispatch` also
refuses to dispatch when that date already has a run.
